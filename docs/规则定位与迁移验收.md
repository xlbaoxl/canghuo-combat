## 3. 三种完成程度不能混同

**存在阶段名称**，说明程序可以记录当前阶段。

**存在事实日志**，说明能记录已经发生的行为。

**存在接入契约**，才说明一个模块能在规定节点收到限定输入、返回受限结果，并由统一执行器实际提交。

当前拥有前两类的较多基础，第三类尚未完整实现。`SPELL_FINISHED`日志不意味着任意Buff已能订阅施法完成；一段状态说明不意味着行为已由数据驱动。验收应实际接入一个测试词条，检查正例、反例和清理，而不是检查类或函数名是否存在。

## 4. 每个规则模块交付什么

在同一规则定义中记录：稳定ID和采用身份、对应接口、来源/持有者/执行者/支付者、读写权限、参数与取整、触发次数作用域、生命周期、失效和取消处理。

普通参数变体使用配置；新增局部行为使用小型处理模块；中断、复活、改时钟等新权限必须公开修改协议，不能通过高优先级任意回调实现。程序封装不改变标准功能句计数，不能把多个独立收益藏进一个Buff名称。

最小样例包括：一个合法生效场景、一个应拒绝或不触发场景、一个与相邻规则组合的场景，以及移除/死亡/到期/读档/AI副本的清理检查。

## 5. 结算明细应该能够回答什么

| 阶段 | 必须可追踪的原因 |
|---|---|
| 预览与核验 | 当前版本、目标与人物快照、实际费用、CD、拒绝原因；不得写状态。 |
| 施法提交 | 资源支付者、前后值、W和恢复窗口、动作/施法ID；失败不部分扣款。 |
| 功能句准备 | 句ID、目标、读取时点、表达式、前句结果；区分未执行和执行为0。 |
| 伤害计算 | 基础量、各修正来源、防护吸收、实际损失、过量及取整位置。 |
| 组后响应 | 父事件、实例、资格依据、执行次序、次数占用与取消原因。 |
| 动作收尾 | 完成/部分中止/终局状态、下一步合法控制；不回滚已经完成的句。 |

例如：`护体增加30 ← 阵势响应D17 ← D17实际气血损失60 ← 伤害请求100、原护体吸收40`。这是诊断结构的算例，不替龟甲阵选择返盾基数。

## 6. 阵法接入验收与待定边界

布阵动作当次结束，只留下可取消的到期任务；不能让一次施法挂起三回合。到期成阵与普通CD恢复不是同一事件。成阵不再次收费、不增加主动作；持阵立即生效后进入自己的CD。

受伤返盾必须读取确定的伤害结果，产生新的护体请求，不回写旧伤害。撤阵需要清理订阅与仍依赖阵势的任务；已并入公共池的护体不能因撤阵而全部清空。

**返盾是否包含护体吸收、布阵/持阵费用、持续与换走处理仍按阵法专题的采用状态管理。**本轮不把默认或选项升为正式值，也不宣称已经做出阵法。
