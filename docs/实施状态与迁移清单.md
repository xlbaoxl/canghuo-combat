## 4. 工程迁入的具体做法与边界

保留`modules/training-camp/`目录以减少路径迁移风险。先原样迁入固定源码，再提交新的仓库入口与来源说明；不要把文档重构和战斗语义修改混进文件搬运。

逐文件记录原路径、目标路径、源commit/blob、SHA256和字节数。确认LFS/实际资源不是空指针、Godot的UID/资源引用完整、素材许可文件保留。引擎、导出模板、缓存、世界存档、账号配置不作为源代码复制。

旧核心策划原件可放历史来源目录保留原文；本仓总纲指向精确采用的主题定义。旧文档中“历史在Git里”指旧仓Git，不得在未迁历史时说本仓已经拥有全部旧提交。

可执行文件和大体积验证截图优先作为本仓Release/归档附件，标明**旧版原始交付**及SHA，不冒充本轮新编译。普通源目录不反复提交EXE。

第一批已确认原件列表见[指纹清单](../migration/artifact_inventory.json)。早期研究任务书与部分学习长报告未找回原始字节；对话摘要已经保留，但物理原件列缺口，不生成同名伪原件。

## 5. 开始重构前必须保留的规则

普通/战机、A/Z/W/R、个人CD、跨格同源等待、支付原子性、公共净结算、前句实际结果、自动与《催》分离、成长不重复放大、现有内容给量、原条件重试都先作为等价基线。

特别是自动内部嵌套响应的执行顺序：不能仅因为拆文件就改成深度优先。新的响应边界若确需不同，必须列行为差异、理由和反例，作为规则修改验收。

目前记录事件不等于通用订阅，Buff文字说明不等于行为定义，模块数量不等于解耦完成。拆出代码后必须能回答某次费用、护体和伤害分别由什么规则贡献。
