# 战斗结算内核：时点、规则接口与诊断

> 1.0｜2026-10-09｜状态：**方向已认可，详细接口为待实现方案**。
> 依据：本会话关于阶段、攻击结算、Buff解耦和阵法的讨论；源码现状基线为旧仓e101fca。不是当前引擎已经具备的模块列表，也不是一次改动全部规则的授权。

## 1. 目标与不做的事

目标不是“每个Buff一个文件”，而是每个Buff的规则在一个位置完整定义，通过少量合法接口参与共同流程，每个结果都能追溯。玩法可以联动，模块不能互相任意写状态。

不制作通用脚本平台、实时联网规则服务或任意连锁编辑器；不照搬别的游戏完整优先权/连锁体系。首版只开放现有玩法和已明确的新阵法需要的能力。新时钟、中断、复活、额外行动属于底层协议变更，不能伪装成一条普通词条。

## 3. 先统一六个概念

**时钟**决定什么推进一次计数；**阶段**规定当前允许处理什么；**命令**是尚待核验的行动意图；**计算请求**是待修正的数值/效果输入；**事实事件**是已经提交的结果；**任务**是将来在指定边界执行的工作。

选择技能、打开说明、预览、动画命中帧都不是“施法已开始”。A/Z满条只是资格，不是进入窗口。注册到期阵法任务不把最初布阵动作挂起三回合。

事实事件不可回写。提交后的治疗不能修改旧伤害数值；后句只能读明确记录，不能用一个全局“上一次伤害”。

## 4. 时钟、阶段与边界

### 4.1 时钟所有权

| 时钟 | 推进条件 | 主要用途 |
|---|---|---|
| t公共刻 | 无活动窗口、响应已稳定，调度需要推进 | 回气、A/Z自然增加、公共周期 |
| W自身窗口 | 合法进入普通或战机窗口一次 | 主动技能CD与声明使用W的延迟任务 |
| R普通回合 | 合法进入自己的普通窗口一次 | 普通周期状态和法宝事件 |
| root/action/cast | 一次动作/施法成功提交 | 支付、次数、奖励与结果作用域 |
| attack/effect_group | 一次独立攻击或共同效果组 | 共享攻防快照、整次攻击消耗、逐击响应 |

一个攻击打三个目标，不等于三次攻击；一次施法有三次攻击，不等于三回合。宠物使用自己的时钟；自动法宝不推进主人W/R。

### 4.2 全局阶段

当前14个阶段先保留。新细节优先作为内部步骤，不为每一类Buff新增一个全局阶段。

`INIT → ENTRY_RESOLVE → DISPATCH → PUBLIC_TICK（需要时）→ WINDOW_PRE → WINDOW_OPEN → DECISION → ACTION_VALIDATE → ACTION_COMMIT → EFFECT_RESOLVE ↔ RESPONSE_DRAIN → ACTION_CLOSE → DECISION或WINDOW_CLOSE → DISPATCH`。

任何确定终局转入BATTLE_END，停止新动作和需存活响应，完成必要记录。已完成的提交不回滚。

新增阵法到期步骤放在W增加、当窗记录重置后，正式窗口开始订阅处理前；这是**下一版方案**。不能把它倒插到尚未通过存活检查的普通窗口前。

主动输入只在DECISION接受。响应期只处理已登记任务，不允许另一个玩家动作插入。UI可暂停表现，不改变逻辑顺序。

### 4.3 普通与战机区别

普通前处理蚀骨，普通结束处理撕裂衰减；战机不重复它们。普通窗口型法宝只订阅NORMAL_OPENED。普通与战机都推进W；战机内多次施法不再推进。满Z登记资格，在安全窗口边界调度，不在多段技能中途插入。

## 5. 一次主动施法的事务协议

1. **预览**：读取快照并经过相同纯解析路径，绝不支付、消耗状态、注册触发或移动随机流。
2. **开始核验**：权限、CD、整门前提、目标与全部开始费用。失败返回原因，不占主动作、不生成CD、不部分扣款。
3. **提交**：一次性支付，记录动作占用、CD、施法ID。主角、法宝自动、独立《催》的支付归属分别处理。
4. **逐句准备**：按CAST_START或GROUP_START读取；缺失前句与结果为0分开；分步费用/消耗仍是明确的局部事务。
5. **计算/提交效果组**：读共同快照，得到合法变化集；统一提交，不让模块直接写H/E。
6. **组后响应**：用确定结果收集合法任务，在指定边界处理。
7. **施法收尾**：标记completed/interrupted/terminal，保存结果，结算符合来源限制的根动作奖励。
8. **交还窗口**：普通主动作已用则关闭；战机回到DECISION。单个Buff不能自行改变下一行动者。

整门“目标须有印记”可以只在开始核验；第一句消费印记后，第二句读取实际消费量，不重新用同一前提把自己判无效。后句失败不回滚已付开始费用及前面效果。

## 6. 伤害与效果计算

### 6.1 固定伤害管线

`确定来源/目标 → 攻击组快照 → 基础效量 → 适用的攻方修正 → 适用的受方修正 → 防护吸收 → 最终变化与状态消耗 → 同组提交 → 同组存亡 → 事实记录/合法响应 → 攻击完成`。

当前没有命中、暴击、护甲或反伤的一般规则，不因为列出扩展位置就自动加入。相关新机制另审。

最低结果包括：base_request、damage_request、shield_absorbed、hp_loss、overkill、nature、hostile、target_id、source、group_id及规则贡献。不同对象的实际结果分开。

### 6.2 不同事实不能混用

- 伤害请求：准备结算多少，不保证实际损失。
- 护体吸收：直接伤害被防护承担的部分，不是气血损失。
- 实际气血受伤：已经提交的损失，可能为0。
- 气血支付：支付结果，不派生“受到伤害”的事实。
- 状态增减：请求层数、实际新增/移除、溢出与最终层数分别记录。
- 治疗：请求、实际恢复、溢出分开；不能把加血与撤销旧伤害混同。

全吸收时不能触发要求hp_loss>0的效果；明确“吸收后”的效果可有另一资格。致死后的返盾不复活，新的致死替代需在提交前有独立协议。

### 6.3 同时组与独立攻击

同一多目标攻击共同读取、共同提交，锋锐等整次消耗不能按目标重复。连续两个独立攻击是两个组，第二组可以看到第一组后的新状态。

公共周期先收集回春、侵袭等请求，再合并提交净收支，不让它们各自先改H并提前判死。当刻新施加状态从下一公共刻参与。模块拆分不能破坏这条约定。

普通技能两击间的自动护体可以影响第二击。当前自动响应内部有防递归机制，多句自动任务的子响应时机不能未经对照直接改成另一种深度优先顺序。**先迁移基线，精确记录嵌套响应的现有行为；新响应契约引起的顺序变化另作显式规则变更与反例测试。**

## 7. 四类标准接口

| 接口 | 输入 | 允许返回 | 禁止行为 |
|---|---|---|---|
| Eligibility资格 | 只读行动意图与状态 | 允许/拒绝及理由 | 扣费、加Buff、推进时间 |
| Modifier修正 | 只读计算上下文、规则实例 | 类型明确的修正贡献、消耗计划 | 随意修改H/E、在查询时消耗次数 |
| Reaction事实响应 | 不可变事件、实例与执行条件 | 有界效果任务 | 回写旧事件、立即递归开回合 |
| ClockTask时钟任务 | 指定时钟、到期节点、实例身份 | 到期效果/阶段转换请求 | 偷用现实时间，凭动画完成触发 |

纯查询必须幂等，重复悬停不能减锋锐。统一执行器验证并提交修正产生的变化计划。规则既可用模板配置，也可用受限小处理器，但不能获任意写状态权限。

来源身份至少区分owner、actor、source_kind/source_id、resource_owner。自动控制不是来源类型：AI操作主角《催》仍适用主动施法规则；法宝自动效果不能通过同一个主人字段误触发主动费用。

## 8. 规则注册表与局内实例

定义记录稳定ID、展示名、标签、叠加方式、合法参数、读数时机、介入接口、计算方式、频次范围、生命周期、冲突组和说明模板。

实例记录instance_id、definition_id、owner/target/source、层数或自有状态、创建/到期时点、监听注册、已预留触发次数、任务ID和生命周期。合池护体仍合池，来源跟踪不等于重写护体算法。

| 已有规则 | 主要接口迁移 |
|---|---|
| 凝神/逆气/撕裂支付 | COST修正，明确合并与下限 |
| 鲸吞/滞气/神速 | PUBLIC_TICK计划修正 |
| 回春/侵袭 | 周期请求贡献＋层数变更计划，统一净提交 |
| 蚀骨 | NORMAL_PRE效果任务 |
| 撕裂衰减 | NORMAL_CLOSED层数变更 |
| 锋锐 | 直接攻击修正＋整组一次消耗计划 |
| 护体 | 防护处理器＋总池上限 |
| 无常印记 | 状态存取，无自动收益 |
| 龟甲阵 | 延迟激活＋受伤事实响应＋持阵主动入口 |

注册表作为行为来源，内容引用稳定ID而不把中文名写进主循环分支；对现有中文存档的迁移要有版本映射，不直接批量重命名后宣称兼容。

清除必须同时处理效果、监听和依赖任务。只删除图标不是移除完成。任务执行前重新检查来源/目标仍有效；过去事件的事实条件不能随意重算。入队预留次数，避免同批多次登记；取消是否归还次数由定义明确，不能默认有时退有时不退。

## 9. 合并、响应排序与可终止性

每种计算明确基础值、加减、乘除、上限/下限、取整的位置。当前算法的顺序首先原样迁移；不强行给所有公式套新的万能乘法顺序。同阶段可交换贡献先汇总；不相容替代需冲突规则，不能靠字典或加载顺序选赢家。

候选响应在事件发生后固定收集；用声明的阶段、事件序号、规则优先、稳定实例序确定顺序。优先级只在允许的同一边界内排序，不能跳过费用或死亡。新注册监听不追溯参与已发生事件。

次数限制必须注明battle/root_action/attack_group/window/normal_round等作用域。反击后代、自动后代和战机奖励分别过滤；不能将“自动”统一免疫，也不能让无界自动连锁靠执行256次截断来假装正常结束。

运行时上限作为异常防护，触及后留因果记录并报错。具体循环的正常终点来自费用、次数、来源限制、消耗或时钟。

## 10. 诊断与可复现

基础记录保留battle、t/W/R、window_kind、root_action、cast、sentence、execution、group、event、parent、规则版本和内容版本。

增加可选详细追踪：基础量；每条修正规则的输入/贡献/理由；防护消耗；实际结果；未触发原因；任务排队/取消理由；来源失效；完整/截断/异常标记。日常模式只保留必要事实，详细诊断可开关，不能为了日志在AI预演中修改真实状态。

追踪示例：`护体+30 ← 阵势实例F2响应伤害D17 ← D17实际损失60 ← 请求100，吸收40`。这解释一次结果，不未经反事实验证就宣称“只改这项必胜”。

同初态、指令序列、随机输入和版本应能重放相同事实。真实执行、预览、AI和快结算共用解析及提交规则；不同决策可以有不同结果。不要复制一份“AI简化伤害”取代同源执行器。

## 11. 模块职责建议

保留battle.gd对外入口，内部逐步分离：时序调度、动作事务、效果提交、规则注册/查询、响应任务、追踪。effect_math继续纯计算；内容编译器校验接口/字段/有界结构；UI和AI只提供意图或读取结果。

这是职责约束，不强制一次增加六个大框架。先抽最清楚的费用修正和周期贡献，再统一伤害/响应；不制作每人物专用脚本，不在主循环写龟甲阵专用if。

## 12. 实施门槛与验收

### K0 固定基线

迁入真实3.0.1项目、内容和既有测试，记录SHA及许可。源目录存在不等于完整可运行；素材缺口必须报告。旧原生UI/Windows烟测保留历史身份，本次未重跑不得改日期称新验证。

### K1 行为等价重构

用相同快照与动作序列比较状态、支付、CD、Buff、普通/战机顺序、终局和自动次数。只允许事先列明的诊断字段差异，不把归一化用于掩盖实质行为变化。先移出11Buff，不改数值和算法。

### K2 可组合扩展

选择两个既有接口组合的新效果作测试内容，证明不改调度即可注册。新增接口本身需要契约、非法输入与冲突测试，不承诺任意能力都纯配表。

### K3 阵法

加入可取消的W到期任务、阵势实例与持阵入口；使用统一伤害事件和护体操作。返盾基数等未定项见阵法文档，不能凭实现便利代定。

最低反例：费用不足无状态变化；反复预览不消费状态；气血支付不算受伤；全吸收不触发实际受伤；多目标不重复消费整次锋锐；独立两击间响应；公共同刻伤害恢复与双方死亡；同源换格不洗CD；战机不推进t/R；自动功效不可手动重放且《催》可独立使用；移除/死亡/读档不重复监听；前句记录不被自动后代污染；取消到期任务不鬼触发；AI副本不污染真实状态；非法/循环规则拒绝加载。

这些为待执行要求，不是本轮已经通过的新增测试。架构合格的标志是：修改一项已定义Buff不需要同步改伤害、法宝、AI和UI四套行为，且仍能定位到具体规则贡献。
